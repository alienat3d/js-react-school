*[Компоненты высшего порядка (HOCs) (180)]*

? 180.0 Здесь мы рассмотрим шаблон «компоненты высшего порядка» или HOC (Higher Order Components), который используется не только в реакте, но и в других фреймворках. К тому же это хороший способ повторного использования логики. Начнём с базовой теории, а затем перейдём к проблемам, которые решает этот способ. Дело в том, что каждый компонент высшего порядка может работать по-разному, поэтому мы сперва изучим общий принцип формирования таких компонентов, а потом рассмотрим частные принципы, которые чаще всего используют в реальности.

180.1.0 Начнём с того, что в Javascript функция может возвращать другую функцию.
<script>
const func = (a) => {
  return (b) => {
    console.log(a + b);
  };
};
</script>

180.1.1 Для вызова такой функции мы пропишем следующий синтаксис. Почему два вызова? Потому, что сперва выполняется первая (наружная) функция, которая вернёт внутреннюю. А затем мы уже вызовем вторую (внутреннюю) функцию, которая "знает" о переданном аргументе первой функции (благодаря свойству замыкания функций) и складывает его с аргументом второй и выводит в консоль.
<script>
func(1)(2);
</script>

180.2 То же самое мы можем написать и с применением класса. Можно сказать, что класс это «красивая обёртка конструктора». И вместо функции внутри мы можем вернуть безымянный класс (это мы уже переходим к классовым компонентам). Здесь у нас функция возвращает безымянный класс, который, в свою очередь, вернёт часть сборки, прописанной у него в функции render.
? 180.3 Именно на таком принципе и работают «компоненты высшего порядка» (HOC, иногда по-русски называют "хоки"). Обычно это функции, которые принимают какой-то компонент и возвращают уже новый модифицированный компонент. Например, "React.memo" — это HOC. Есть и многие другие, которые будут нам встречаться. По большей части нам не так уж и важно, что у них под капотом, но этот приём важно знать, т.к. его можно использовать для оптимизации работы или для добавления новых свойств готовым компонентам.
<script>
const classFunc = () => {
  return class extends Component {
    render() {
      return <h1>Hello world!</h1>
    };
  };
};
</script>

? 180.4.0 Часто в приложениях у нас будут похожие компоненты с совсем небольшим отличием — логика у них одинаковая, но приходить в них будут разные данные. Здесь у нас не случайно два слайдера, которые в целом делают одно и то же, но с небольшими отличиями по функционалу. И вместо того, чтобы делать копии кода очень похожих компонентов, мы могли бы это оптимизировать. 
? 180.4.1 А если подумать о более реалистичных примерах, то это могли бы быть похожие компоненты, которые рендерят немного разную вёрстку, но при этом ещё и получают разные данные. Один компонент может рендерить список товаров, а другой — список пользователей. И это могут быть компоненты в разных частях фронтенда. Один компонент будет рендерить список товаров для клиента, в то время, как другой рендерит те же товары, но уже в панели администратора с более расширенными функциями и доп. информацией. И в таких случаях нам бы хотелось общую логику вынести в отдельное место, а при необходимости ещё передавать разные пропсы.
