*[Принцип конечного автомата, FSM Finite state machine и 1 подход к состояниям (187)]*

? 187.0 Здесь мы рассмотрим концепцию конечных автоматов, понятие стейт-машин (машин состояний). Это достаточно сложная
университетская тема, которая часто в сразу не бывает ясна и понимается до конца во время практики, но это необходимая
база для программиста.

Рассмотрим эту тему сразу на практике на pet-проекте «Comic
Wiki»: [\projects\react-marvel-wiki\src\components\charInfo\CharInfo.js]

? 187.1.2 И как раз для таких задач существует «концепция конечного автомата» — это такая сущность, которая имеет
определённое количество состояний. Эта сущность в один момент времени может быть только в одном активном состоянии и
чтобы изменить этот элемент мы меняем его состояние. Можно представить как пример курьера, у которого, допустим 4 разных
состояния: ожидание, получение заказа, доставка и получение оплаты. У каждого из состояний есть определённый набор
действий, который курьер может выполнять, пока он в этом состоянии: пока он в первом состоянии он может общаться с
коллегами, читать свой смартфон или гулять себе вокруг склада. Как только он переходит ко второму состоянию, то у него
появляются новые действия и блокируются другие, свойственные первому состоянию. Теперь он уже таскает товары к себе в
машину и отмечает в списке какие товары он получил и изучает адреса, в которые он должен их довезти и составляет маршрут
следованья. Дальше он переходит к доставке и у него опять новый набор действий, а прежние становятся недоступны и т.д.
Точно также и с элементами, в разных состояниях у них разный вид и разный доступный список, что они могут (или с ними
можно) сделать. Всё это и называется «концепцией конечного автомата» и это концепция по своей сути математическая
модель, применяемая много где в программировании, в нейросетях, в играх и др. сферах. Английское название этой
концепции — Finite State Machine (сокр. FSM), иногда в устной речи называют "стейт-машины" или "машины состояния". По
большому счёту любое приложение или скрипт, который использует состояния и меняет их — можно назвать стейт-машиной.

? 187.1.3 Пока что мы уже использовали часть концепции конечного автомата, состояния, которые меняются у нас есть, но
нам ещё осталось автоматизировать процесс. Вернёмся ненадолго к уроку про
«useReducer» [см. \projects\mini-projects\react-slider\comments\179-App.js], там мы меняли стейт многими способами,
используя только 1-у функцию "dispatch", в которую передавался какой-то "action". И в зависимости от того, какой тип
экшена передавался, то выполнялось соответствующее действие внутри функции reducer. Это очень близко к концепции "
стейт-машины", т.к. существует конечное кол-во стейтов (состояний), описанные в case, которые мы переключаем через 1
функцию. Redux будет построен на таком же принципе. Важный нюанс: стейт-машины могут быть реализованы по-разному,
потому, что это именно концепция, а не конкретная техника исполнения. Главное, чтобы соблюдались базовые принципы:
конечное кол-во состояний, механизм перехода, удобный функционал отображения и лишь 1-о активное состояние.

187.1.4 В нашем примере здесь у нас уже есть всё, кроме удобного отображения. Конечное кол-во состояний есть — это
loading, error и char. Механизм перехода тоже есть — когда мы выполняем запрос, механизм может переключить на ошибку, на
загрузку, а в случае успеха — переключит на стейт с данными о персонаже. Ну, а ещё у нас есть состояние, которое
показывает, что даже, когда ещё ничего не произошло мы отображаем компонент Skeleton. Итак, у нас тут 4 состояния и
механизм перехода между ними. Кроме этого у нас всегда лишь одно активное состояние. Единственного, чего нехватает —
удобного отображения.

187.1.5.0 В Первой статье «Машины состояний и разработка веб-приложений» в ссылках хорошо описана концепция конечного
автомата с примером создания машины состояний средствами JavaScript:
187.1.5.1 Здесь создаётся переменная "machine", куда помещается объект, в котором есть разные свойства — это состояния
стейт-машины. В этом примере у нас состояние "покоя" (idle), "идёт запрос на сервер" (fetching) и "ошибка запроса" (
error). У каждого из состояний свой набор методов, т.е. функций, которые могут выполняться только тогда, когда активно
это состояние.
<script>
    const machine = {
      'idle': {
        click: function () { /* code */ }
      },
      'fetching': {
        success: function () { /* code */ },
        failure: function () { /* code */ }
      },
      'error': {
        'retry': function () { /* code */ }
      }
    };
</script>

187.1.5.2 Далее рассмотрим модификацию это стейт-машины: теперь есть свойство "state", которое отображает текущее
состояние. Также есть свойство "transitions", которое отвечает за переходы.
<script>
    const machine = {
        state: 'idle',
        transitions: {
            /* 187.1.5.8 И на примере события click мы рассмотрим первое действие, которое нам нужно диспетчеризировать и вот как может выглядеть обработчик события: когда запускается метод "click", то мы сменим активное состояние с "idle" на "fetching", затем идёт запрос на сервер функцией "getData" и в чейн-методе then мы в конструкции try...catch мы запустим метод "dispatch" с разными аргументами, в зависимости от того, какой результат вернулся из функции getData (успех или ошибка). Здесь у нас получилась замкнутая система, где одно состояние переходит в другое, находящееся внутри стейт-машины. */
            'idle': {
                click: function () { 
                    this.changeStateTo('fetching');
                    service.getData().then(
                        data => {
                            try {
                                this.dispatch('success', JSON.parse(data));
                            } catch (error) {
                                this.dispatch('failure', error);
                            }
                        },
                        error => this.dispatch('failure', error)
                    );
                }
            },
            /* 187.1.5.10 Расширяем пример дописывая действия для других состояний. Вывод данных в success. И обратим внимание на то, как мы избавили себя от необходимости думать о предыдущем процессе. Мы не заботимся о щелчках пользователя по кнопке, или о том, что происходит с HTTP-запросом. Мы знаем, что приложение находится в состоянии "fetching", и мы ожидаем появления лишь этих двух действий. Это немного похоже на создание новых механизмов приложения, которые работают в изоляции. */
            'fetching': {
                success: function (data) { 
                    this.changeStateTo('idle');
                 },
                failure: function (error) { 
                    this.changeStateTo('error');
                 }
            },
            /* 187.1.5.11 также заполним состояние "error". Создадим тут код для реализации повторной попытки, в результате приложение сможет восстановиться после возникновения ошибки. ↓ */
            'error': {
                'retry': function () { 
                    this.changeStateTo('idle');
                    this.dispatch('click');
                 }
            }
        },
        /* 187.1.5.3 А здесь будет механика переходов между стейтами, чтобы состояния стейт-машины менялось. Как и в рассмотренном уже хуке «useReducer» здесь участвует метод "dispatch" и передаётся какой-то экшен, который здесь назван "actionName" */
        dispatch(actionName, ...payload) {
            /* 187.1.5.4 Действия (actions) формируются из сбора всех методов доступных в текущем стейте (установленном в свойстве активного стейта "state"). */
            const actions = this.transitions[this.state];
            /* 187.1.5.5 И мы создадим также одно действие, которое в данный момент мы собираемся выполнить. */
            const action = this.transitions[this.state][actionName];

            /* 187.1.5.6 Если это действие было найдено, то мы добавляем его к нашей стейт-машине. */
            if (action) {
              action.apply(machine, ...payload);
            }
        },
        /* 187.1.5.7 А также у нас тут метод смены состояния, т.е. записи нового стейта в свойство активного стейта "state". ↑ */
        changeStateTo(newState) {
          this.state = newState;
        },
    };

    /* 187.1.5.9 ↑ */
    machine.dispatch('click');
</script>
