*[React Context и useContext (178)]*

? 178.0 На текущий урок всю базу Реакта мы по сути изучили, теперь переходим к изучению правильного построения архитектуры приложений. Существуют разные подходы к построению архитектуры приложения и два вида подходов мы уже рассмотрели: 1) В CRUD-приложении со списком сотрудников мы применили подход с одним общим стейтом в главном родительском файле, а потом прокидывали его в методы для изменения его состояния ниже по иерархии компонентов; 2) В приложении «ComicVine Wiki» у каждого компонента был собственный стейт или набор стейтов и менялись они в нём часто автономно; 3) Ещё есть подход, когда существует общий глобальный стейт (на подобии приложения списка сотрудников), но при этом каждый компонент может с ним взаимодействовать без прокидывания пропсов. Какой из подходов выбрать — зависит от характера приложений, какие действия оно совершает и его сложности, а также глубины вложенности друг в друга компонентов. Например, если сравнить два наших тренировочных проекта на этом курсе, то они очень разные — в списке сотрудников компоненты тесно связаны друг с другом, а в Wiki — нет.
? 178.1 Итак, React Context это и есть тот самый 3-й подход к построению архитектуры приложения с глобальным стейтом, о котором говорилось выше. «Контекст» нужен для того, чтобы передавать данные через дерево компонентов без необходимости передавать пропсы на промежуточных уровнях. В типичном React-приложении данные передаются сверху вниз с помощью пропсов (от родителя к дочернему компоненту). Однако, такой способ может быть чересчур громоздким для некоторых типов пропсов (например, выбранный язык, UI-тема и т.п.), которые необходимо передавать во многие компоненты в приложении. Контекст предоставляет способ делиться такими данными между компонентами без необходимости явно передавать пропсы через каждый уровень дерева (т.н. «props drilling»).  

Рассмотрим на тестовом примере: [\projects\react-project-1\src\components\Form3ClassComponent.js]

? Приложение может использовать несколько контекстов, давая доступ компонентам к определённой группе данных. Тогда под каждый контекст нужно создать отдельный Provider со своими данным в атрибуте "value" (можно в один Provider помещать другой Provider).
